UFS LM4-NUOPC-driver 한눈에 이해하기

GFDL Land Model v4를 UFS 기상모델에 붙이기 위한 "연결 어댑터" 서브모듈
MOF KIMST · LSM 진단 testbed 참고자료
TL;DR — 30초 요약

LM4-NUOPC-driver는 LM4(육지모델) 그 자체가 아니라, LM4를 UFS 결합 프레임워크에 꽂기 위한 NUOPC 어댑터(cap)입니다. 이 저장소 안에 LM4 본체가 git submodule로 들어있고, 그 위에 "UFS 표준 플러그"를 씌운 구조입니다.

즉 — LM4를 노트북(UFS)에 연결하는 USB-C 어댑터라고 보면 됩니다. 어댑터(driver)와 기기(LM4)는 별개지만 한 상자(repo)에 같이 들어있습니다.

1. 먼저 용어 3개만

  • LM4 — GFDL Land Model version 4. 미국 GFDL의 육지모델로, GFDL 기후모델 CM4 · ESM4 · SPEAR의 land 컴포넌트입니다. 식생·눈·토양·하천유출까지 다룹니다.
  • NUOPC — 여러 모델(대기·해양·육지)을 표준 방식으로 결합하기 위한 규약(ESMF 기반). 각 모델은 NUOPC cap(얇은 래퍼)을 갖춰야 결합 가능.
  • UFS — Unified Forecast System. NOAA의 통합 예보 시스템 우산 저장소 (ufs-weather-model). 대기(FV3)·해양·해빙·육지 등을 submodule로 모아 결합 실행.
핵심: UFS는 "여러 모델을 모으는 우산"이고, LM4가 그 우산에 들어가려면 NUOPC cap을 입은 driver 형태여야 합니다. 그게 바로 LM4-NUOPC-driver.

2. driver(cap)가 왜 필요한가

🔌
비유: LM4는 "성능 좋은 외장 모니터"입니다. 그런데 UFS라는 노트북은 NUOPC라는 규격의 포트만 받습니다. LM4를 그냥은 못 꽂으니, NUOPC cap = 어댑터를 끼워야 합니다. 이 어댑터가 하는 일:
  • 대기에서 오는 입력(기온·바람·복사 등)을 LM4가 이해하는 형태로 변환
  • LM4의 출력(land fraction 등)을 UFS 중재자(CMEPS)에게 전달
  • 실행 순서·타임스텝(빠른 육지과정 ↔ 느린 육지과정)을 UFS 시계에 맞춤

3. 저장소 구조 (submodule 관계)

UFS는 중첩 submodule 구조입니다. 위에서 아래로 들어갑니다:

ufs-weather-model/ # ① UFS 우산 repo (최상위) └── LM4-driver/ # ② = NOAA-GFDL/LM4-NUOPC-driver (이 글의 주인공) ├── nuopc_cap/ # NUOPC 어댑터 코드 (Fortran) ├── LM4/ # ③ LM4 본체 = 또 다른 submodule (gitlab.gfdl) ├── CMakeLists.txt # CMake 빌드 정의 ├── lm4_src_files.cmake # 소스 파일 목록 └── *.IN / *.nml.IN # 설정 템플릿 (ufs.configure, namelist)
즉 LM4 본체는 submodule 안의 submodule입니다. git submodule update --init --recursive로 재귀적으로 받아야 LM4 소스까지 내려옵니다. 빌드는 CMake, 코드의 ~97%가 Fortran입니다.

4. UFS 안에서 어디에 위치하나 (결합 그림)

🌍 대기 컴포넌트 (FV3 atmosphere) 또는 offline 시: CDEPS 데이터 대기 (DATM)
⇅flux 교환
⚙️ CMEPS 중재자 (Mediator) 컴포넌트 간 격자 보간·flux 중계 — 1st-order conservative
⇅
🔌 LM4-NUOPC-driver (cap) UFS ↔ LM4 변환 어댑터
⇅
🌱 LM4 본체 식생·눈·토양·하천유출 물리

대기와 육지는 직접 대화하지 않습니다. 항상 CMEPS 중재자를 거쳐 주고받습니다. driver의 cap은 LM4 쪽 "통역사" 역할입니다.

5. 무엇을 주고받나 (import / export)

⬇️ Import — 대기→LM4 (받는 것)

  • 기온 (temperature)
  • 기압 (pressure)
  • 바람 성분 (u, v wind)
  • 비습 (humidity)
  • 하향 복사 — 장파(LW)·단파(SW) 성분
  • 강수 (precipitation forcing)

⬆️ Export — LM4→중재자 (내보내는 것)

  • land fraction (lnd%sg_landfrac)
  • 지면 flux(현열·잠열)·알베도·지면온도 등 (결합 단계에서 확장 중)

현재 export는 결합 완성도에 따라 계속 추가되는 중. offline 테스트는 import(대기 forcing) 위주로 검증.

6. LM4 vs Noah-MP (UFS의 두 육지모델)

UFS는 육지모델을 두 개 품고 있습니다. 둘 다 NUOPC cap으로 붙습니다.

항목LM4 (GFDL)Noah-MP
성격지구시스템급 육지모델수치예보용 경량 육지모델
식생동역학 식생(PPA), 다층 캐노피, 페놀로지, 산불·작물주로 규정형(prescribed) 식생
탄소/생화학CORPSE 토양탄소, 다중 탄소 풀제한적 (옵션)
수문예단적 하천유출, 수온 추적 tracer토양수·눈 중심
UFS 결합 driverLM4-driver (NUOPC cap)NOAHMP-interface (NUOPC cap)
주 용도S2S·기후, land-atmosphere 상호작용현업 단기·중기 예보
과제 관점: 다중 LSM 비교(JULES · CLM5 · Noah-MP · LM4)에서 LM4는 "식생·생화학까지 가장 복잡한 쪽" 끝에 위치. Noah-MP는 "현업 경량" 쪽 끝.

7. 빌드 · 실행 · 현재 상태

  • 빌드: CMake. 현재 global C96 cubed-sphere 격자 지원.
  • offline 모드 가능 — CDEPS(데이터 컴포넌트)로 관측 대기 forcing(GSWP3)을 먹여 LM4만 단독 구동·검증. 회귀시험(regression test) 2종 제공 (ufs.configure.atm_lm4.IN).
  • 결합 모드 진행 중 — FV3 대기와 2-way 결합 및 S2S 규모 평가가 현재 개발 단계.
  • restart: FMS 기반, 9개 restart 파일 필요.
🎯
통합 동기: 강수 극값·S2S 예측력. 지면-대기 상호작용이 계절내~계절 규모 예측의 중요한 예측가능성 원천이고, LM4의 정교한 캐노피·눈·토양 물 교환이 거기에 기여한다는 것이 NOAA/EPIC의 통합 명분입니다.

8. MOF LSM 과제와의 연결

우리 과제(해수부 차세대 해양기후모델 LSM 진단)의 Phase 1 testbed 4종 중 하나가 LM4+입니다. 이 driver가 그 진입로입니다:

  • 오프라인 testbed로 바로 활용 가능 — CDEPS + GSWP3 경로가 이미 있으니, 우리가 받는 forcing(ERA5 / Sheffield-PGF / CMFD)을 같은 DATM 틀에 먹이면 JULES·CLM5와 동일 forcing·동일 격자로 LM4를 굴려 비교할 수 있습니다.
  • 빌드 난이도: CLAUDE.md 메모대로 "FMS 프레임워크 별도 빌드 필요" — 중첩 submodule(LM4)과 FMS·CMake 의존성이 JULES보다 무겁습니다. climate00에서 먼저 offline 회귀시험부터.
  • 진단 포인트: ILAMB/PLUMBER2 틀에서 LM4의 동역학 식생·하천유출이 Noah-MP/CLM5 대비 land-atmosphere coupling 지표(Mi, λ)를 어떻게 바꾸는지가 비교 핵심.
다음 액션 후보(나중): climate00에서 LM4-NUOPC-driver를 --recursive로 clone → CDEPS+GSWP3 회귀시험 1개 빌드·실행 성공시키기.
